# Groundwork v2 0.2.0-preview.1

This release is a clean-break preview schema boundary. All public packages in
the release use the exact version `0.2.0-preview.1` and are published only to
the Valence Works Groundwork Feedz source.

## Candidate 1.0 contract freeze

The complete exported API for both runtime target frameworks and the complete
source-emitted `GW-*` diagnostic set are now committed under `eng/` and checked
byte-for-byte by `Groundwork.Architecture.Tests`. Any baseline change is
therefore review-visible and must carry its compatibility assessment, release
note, and migration guidance.

The versioning policy now defines concrete 1.x rules: patches remain source and
binary compatible; minors may add APIs and diagnostic codes; existing codes are
never reassigned; deprecated APIs remain functional throughout 1.x; and removal
waits for the next major version. It also defines the final preview-to-1.0
transition. Operators should inspect and back up deployed catalogs, use
`groundwork adopt` for verified Groundwork-shaped catalogs without applicable
history, and use authorized schema/data migrations where possible. Recreation
is the last resort when the 1.0 release note identifies a physical boundary
that cannot be safely adopted or migrated.

## Production support policy

Provider status now uses named **Production-supported**, **Compatibility-only**, and
**Development/reference-only** tiers instead of “conformance-passing / preview.” SQLite is
production-supported only as a file-backed, single-writer deployment; the live-tested MySQL 8.4.6,
PostgreSQL, and SQL Server topologies require their documented writable primary; and MongoDB
production support is limited to its live-tested transaction-capable replica-set topology. Other
MySQL 8.0.17+ releases, MariaDB 11.4.13+, MongoDB sharded clusters, and MongoDB standalone are
compatibility-only until matching live evidence exists. `Groundwork.Testing` remains
development/reference-only.

The policy names incident ownership and adds deployment, triage, recovery, schema, and data-migration
runbooks. Groundwork maintainers own reproducible package defects inside a supported topology;
operators continue to own the database/platform, credentials, capacity, backup/restore, upgrades,
and failover. Support is best effort and does not promise response or availability times. See the
[support matrix](../support-matrix.md) and [production operations](../production-operations.md).

## Security-boundary hardening

- Exact `groundwork apply`/`adopt --expected-plan` authorization now requires
  `--deployment-id`. The non-secret identity participates in the fingerprint,
  preventing a plan reviewed for one deployment from authorizing another.
  Supplying `--safe` alongside `--expected-plan` does not weaken that binding.
  Connection strings can be supplied through `--connection-env`,
  `--connection-file`, or `--connection-stdin`; the modes are mutually exclusive
  with legacy `--connection`, and resolved secrets are redacted from CLI and
  provider errors, including sensitive key/value fragments and reordered forms.
  `schema emit` refuses connection-input flags because it performs no provider I/O.
- Privileged cross-scope queries now require an `IStorageAccessObserver` and
  emit `query-across-scopes.attempt`, `.success`, or `.failure`. A missing sink
  or a sink that cannot record the attempt fails before provider I/O. Audit
  failure cannot erase the original provider failure; when both fail, the
  aggregate preserves both causes. The legacy one-shot audit helper is obsolete.
  Audit identity and purpose remain caller-supplied labels; hosts must bind them to
  their authenticated operation context.
- Direct casts to `ISetMutationStorageSession` can no longer bypass query
  coverage or explicit scan acceptance. Shipped relational, MongoDB, and
  unit-of-work seams require internal admission evidence from the public
  set-mutation extensions before native work, refusing direct calls with
  `GW-COVER-001`. Provider packages remain trusted code; the provider conformance
  suite now verifies that implementations advertising set mutation fail closed
  on a direct capability call.
- `IDataMigrationTransform` adds the required `Version` member. Identity and
  version/content digest are fingerprinted together for durable replay, and
  transform output is validated provider-neutrally for nullability, CLR type,
  the portable Double value domain, length, and decimal precision/scale before
  provider execution. Direct migration runs now hold an exclusive durable target
  lease for the full pass, closing the concurrent read-then-start replay window.
  MongoDB renews that lease on a background heartbeat throughout long chunks and
  verifies ownership again before accepting progress. SQLite uses an exclusive
  cross-executor file lock for file-backed databases rather than a process-local
  no-op.
  `IDataMigrationExecutor` implementations must add `AcquireMigrationLock` and
  advertise `ExclusiveRunLease`. This is a source-breaking preview change:
  transform implementations must add a stable
  version and change it whenever their output logic changes. Existing preview
  ledger rows were recorded under the older identity-only fingerprint and do
  not silently rebind. Finish in-flight work and back up before upgrading, then
  give the upgraded declaration/catalog a new semantic migration identity and
  explicit version so its reviewed deterministic transform can run under new
  evidence. Do not edit a completed provider ledger row to look compatible.
- Security guidance now states the remaining boundaries explicitly: plan
  fingerprints are intent/TOCTOU gates rather than authentication, audit labels
  are not authenticated principals, adoption verifies shape rather than row
  meaning, and multi-target apply/adopt can have a partial outcome. See
  [security boundaries](../security-boundaries.md).

## Required SQLite catalog reset

`Groundwork.Sqlite` now stores portable ordinal strings with the registered
`GROUNDWORK_UTF16_ORDINAL` collation. Ordinary indexes inherit that same
collation, so equality/range predicates and index ordering use the required
.NET UTF-16 ordinal semantics—including supplementary characters—and native
plans can use the declared indexes.

SQLite catalogs created by an earlier v2 preview physically declare those
columns as `BINARY`. They are not compatible with this corrected persisted
schema contract. Delete and recreate every such preview catalog, then apply
the current storage declarations before writing data. There is deliberately
no migration, alias, dual-write, fallback, or compatibility mode.

PostgreSQL, SQL Server, and MongoDB declarations do not require a physical
catalog reset for this specific correction. Applications should nevertheless
move their complete Groundwork v2 package closure to the exact release version
rather than mixing preview package versions.

## MongoDB declared-key coverage is now a native seek

MongoDB physical schema targets now include an ordered native index over the
declared key fields whenever no declared index already has the same leading
prefix. This preserves the provider-neutral rule that a composite key such as
`(tenant, id)` covers equality on `tenant` as well as the complete key. Live
explain assertions now prove the leading-key query is an `IXSCAN` on MongoDB
and an index seek on SQLite, PostgreSQL, and SQL Server.

This changes MongoDB's persisted physical target and fingerprint. Apply each
MongoDB declaration before opening sessions after upgrading; Groundwork will
create the provider-owned `groundwork_declared_key` (with a deterministic
numeric suffix on name collision). Runtime admission treats the chosen
key-serving index as process-required and refuses a missing or changed copy,
while ordinary declared-index drift remains observable/degraded as before. No
data rewrite or catalog reset is required.

## SQL Server effective parameter budget

`Groundwork.SqlServer` now advertises and enforces **2,098 caller-owned bind
parameters** per command. SQL Server's 2,100 statement limit reserves two
parameters for the `Microsoft.Data.SqlClient` `sp_executesql` wrapper, so
queries that previously relied on 2,099 or 2,100 application parameters now
refuse with `GW-QUERY-015` before provider I/O. Applications that reach this
boundary should split the membership or page it into smaller requests. Keyed
batch reads retain their existing 2,098-key budget; the driver overhead is not
subtracted a second time.

## Other changes

  `IModel` metadata, or a migrations snapshot model into actual kernel `StorageUnit` declarations.

  require the exact deployment plan authorization; in-process `Schema.Apply` refuses the protected

  MySQL/MariaDB projects ticks as microsecond-precision `DATETIME(6)`. A scoped view includes all

  implicitly commit. MongoDB and the in-memory provider fail closed because they cannot provide one
  stable relational view. Name collisions are refused before schema I/O with `GW-PORT-015`.

  preserve their reflected members or supply generated JSON/record metadata. A cost-braked,
  exact-head `Native AOT conformance` workflow packs the public package closure, restores an isolated
  package-only consumer, verifies that `PublishAot` produced an ELF/Mach-O executable, and runs the

- `Groundwork.Schema.Generator` now emits direct getters and constructor/member materializers for
  `[GwTable]` CLR rows plus factories for supported LINQ `Select` constructor, initializer, record,

  `Convert.ChangeType`, and the Records benchmark now asserts `dynamic_codegen=0` instead of merely
  checking that reflection stayed outside the row loop. Add the generator to applications preparing

  matching the existing PostgreSQL and MySQL/MariaDB bootstrap guards. Concurrent schema applies to

  targets. Instances running this release that apply different declarations therefore wait rather

  shape, matching analyzer and schema-tool admission while retaining the deployed-catalog
  intersection. Privileged cross-scope sessions fail closed without exposing provider-owned scope
  columns in coverage diagnostics.
- A no-change relational schema apply now treats index-only catalog drift as the same observable,

  reference. `ReferenceJoin` carries the ordered source-to-target-key equality pairs, and joined
  requests require every `ColumnRef` to be qualified as either the source or target table; unqualified
  element-set predicates remain refused until they gain a side identity. Join identity participates

  intentionally versioned from `q2` to `q3`, invalidating preview-era recognized-shape inventories

  Joined ordering preserves one nested-loop-compatible lexicographic shape: a non-empty contiguous
  driving segment followed by an optional target segment; target-only and interleaved orders refuse.
  The legacy single-table overload fails closed for joined requests instead of treating an index

  deployed candidates on both sides. Analyzer lowering (`#167`) and relational rendering (`#168`)

  share one parameter budget across both sides and paging, and expose every effective continuation

  `__groundwork_target`. Provider admission resolves the target's exact physical collection from
  durable applied history under the source session's scope instead of deriving a name from the
  source collection. Reference snapshots now persist an optional target-scope policy and include
  it in their fingerprint when present. Manifest compilation and target-object builder declarations

  declarations; a direct legacy declaration that still omits the policy remains readable, but
  MongoDB refuses its joins before target metadata I/O.

  Scoped relational declarations now accept the provider-owned scope prefix on an otherwise
  reference-covering index, and native joins bind both relations to the session's scope so equal
  logical keys in another scope cannot participate in the result.
  Privileged cross-scope queries continue to refuse every join with `GW-ACCESS-003` before audit
  observation or provider commands.
- `Groundwork.Query.Linq` can now bind a direct typed navigation to an existing provider-neutral

  qualified driving-key tie-breaks, then the declared target key in reference order. Continuation
  ordering and provider-page projection metadata keep same-named columns on opposite sides distinct.
  Joined continuation options carry the
  complete declared driving identity and validate its type/facet metadata against the provider-resolved

  returns nullable `Int64`/`Decimal`; closed `Min`/`Max` overloads accept the supported orderable

  `Skip` pages fail closed as `GW-LINQ-113`, and reductions after `Select` fail closed in both the
  runtime and analyzer. Reduction targets participate in index coverage and use `GW-LINQ-112`,
  `GW-SEM-AGG-001`, and `GW-SEM-AGG-002` for non-portable selectors. Async `SumAsync`, `MinAsync`,
  and `MaxAsync` now dispatch through a safe scalar executor seam; all four providers render these
  reductions natively, applying distinct and input paging before aggregation without client-side
  row fallback. Nulls are ignored, no-non-null input returns null, and integer sums are nullable
  `Int64`.
- External implementations of `Groundwork.Query.Linq.IGwQueryExecutor` must implement the new
  abstract `ReduceAsync<TResult>(QueryRequest, CancellationToken)` method. The
  `Groundwork.Query.Linq` contract now requires that method to dispatch reductions to a
  provider-native scalar execution path; adapters that only support row materialization must add
  this method before upgrading.
- SQLite no longer risks pooling a connection whose rollback failed while its
  native transaction stayed open. Microsoft.Data.Sqlite marks a transaction
  "completed" in a `finally` block regardless of whether the ROLLBACK it issues
  succeeds, so a rollback that fails under contention still let a poisoned
  connection return to the pool looking clean; the next caller to draw it saw
  "cannot start a transaction within a transaction" or a refused PRAGMA for
  unrelated work. `SqliteUnitOfWork` and `SqliteStorageSession`'s single-write
  path now share one guard that clears the connection-string pool group when a
  rollback fails, discarding that connection instead of recirculating it. The
  standalone session path also closes and retires its checked-out connection
  and becomes unusable, so it cannot issue another write against a stranded
  native transaction. For shared in-memory sessions, the provider is retired
  as a whole so sibling sessions cannot use a closed shared connection. The
  pool clear also tears down every idle connection
  sharing that connection string in-process, and
  marks every other checked-out one non-poolable, as the price of a failure
  path that is otherwise rare.
- `IStorageProviderConnection.OpenOwnedSession` now provides a deterministic per-caller session
  lifetime across all providers. Owned relational sessions use independent connections and return
  them on synchronous or asynchronous disposal; MongoDB and in-memory sessions enforce the same
  release/use-after-dispose contract. The dependency-injection `IGroundworkStorage` opens and
  releases owned sessions with each scope, so request-scoped access does not retain one provider
  handle per request.
- This is a deliberate source-contract change for third-party providers: implementations of
  `IStorageProviderConnection` must add `OpenOwnedSession`. Implementations of `IGroundworkStorage`
  must also implement `IAsyncDisposable`, and `IOwnedStorageSession` implementations must report
  their idempotent release state through `IsReleased`; existing legacy `OpenSession` and unit-of-work
  sessions remain non-owning and do not implement `IOwnedStorageSession`.
- Relational batch fallbacks now reuse their active batch transaction without reacquiring the
  non-reentrant shared-session gate. Independent callers remain serialized on shared sessions,
  while owned sessions bypass that gate because their connections are independent. This addresses
  #207's captured 23-hour PostgreSQL dump (PID 25945): `ApplyBatchAsync -> ExecuteWrite` held the
  connection `SemaphoreSlim` while `ApplyBatchFallback -> ConditionalUpsertAsync -> Execute`
  attempted to reacquire it; the regression now completes the same fallback under a bounded timeout.
- SQLite, PostgreSQL, and SQL Server now run exact and status-only append idempotency through one
  shared relational state machine while retaining their native ledger, clock, claim, and payload
  SQL. Claim-race entries with an empty fingerprint now consistently refuse exact replay with
  `GW-APPEND-002`, expired-row deletion is conditional on the timestamp that was observed, and a
  payload commit is rolled back unless every input has one successful outcome and the ledger result
  update affects exactly one row.
- Relational retention batching and exact-retention replay now use one shared state machine across
  SQLite, PostgreSQL, and SQL Server while retaining provider-native victim selection, clock, and
  ledger SQL. Exact-retention replacement deletes only the expired ledger row that was observed,
  and target-row deletes are rolled back unless the exact result updates one durable claim row.
- External relational providers can now derive their required session surface from

  `RelationalStorageSessionAdapter`, and construct the shared staging/terminal-state lifecycle with
  `RelationalUnitOfWork`, `RelationalUnitOfWorkSession`, and `RelationalUnitOfWorkLifetime` without
  friend access. `RelationalAppendAdapter` and `RelationalRetentionAdapter` keep only native commands
  provider-owned while the base owns validation, durable claim/replay, direct-write transactions,

  `GET_LOCK` leases connection-bound; and supplies runtime admission, schema coordination, exact

  `docs/v2/mysql-provider-evidence.md` records the reproducible provider-LOC comparison.
- `IStorageSession.BatchRead`/`BatchReadAsync` add a keyed batch-read primitive
  that chunks unbounded key sets under provider-owned parameter and payload
  budgets, preserving the injected scope parameter for relational sessions and
  staying conservatively below MongoDB's BSON command-size ceiling. When no
  connection is supplied, the shared planner applies a 15 MiB payload fence;
  an explicit admission profile can advertise a different deployment budget.
  Results are merged in caller key order and report unmatched representatives
  through `MissingKeys`; folded string equivalents use the persisted search key,
  occur once, retain the first requested spelling, and refuse a mismatched
  `ColumnRef` policy with `GW-QUERY-031`. Invalid table, key, or provider result
  contracts refuse with `GW-BATCHREAD-001` through `GW-BATCHREAD-003`; an
  individual key that cannot fit refuses with `GW-BATCHREAD-004`. MongoDB now
  advertises its lack of a bound-parameter ceiling explicitly, while ordinary

## Nonportable coverage refusals do not suggest an index

`GW-COVER-016` means the query shape itself cannot be represented by a portable
ordered index. Provider-default null ordering, ordering a Boolean, Double, or
Binary column, a nonportable range, a cross-column `Or`, and other predicates
that are not representable by an ordered index now omit the `Add: [GwIndex(...)]`
line from their refusal message. Declaring another index could not clear those
refusals; rewrite the query into a portable shape where possible, or mark the
read with `.AcceptScan(...)`. An otherwise actionable `GW-COVER-005` remains
unchanged and includes its index suggestion when no `GW-COVER-016` refusal is
also present.
