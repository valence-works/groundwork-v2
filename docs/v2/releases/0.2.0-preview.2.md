# Groundwork v2 0.2.0-preview.2

This release marks a **persisted schema boundary**. All public packages in the
release use the exact version `0.2.0-preview.2` and are published only to the
Valence Works Groundwork Feedz source.

## Required catalog discard

The canonical schema document now carries every lifecycle policy the fluent
kernel builder can declare: portable column defaults, scope policy, optimistic
concurrency, timestamps, retention, append and retention idempotency, and
aggregation profiles. The deployment tool compiles a declared schema through the
provider's own physicalization, so a tool-applied target and the target a runtime
session expects are one value rather than two that happen to agree. Declared
indexes and aggregation profiles are now sets rather than sequences: naming the
same ones in a different order describes the same subject.

Each of those corrections changes subject fingerprints, and an applied catalog
records the fingerprint it was applied under. A catalog created by an earlier
preview therefore cannot be reconciled with these declarations, and re-applying
is not the remedy — the tool refuses to read that catalog at all.

**Discard every catalog created by an earlier preview and create a fresh one
from the current declarations.** Groundwork ships no in-place migration,
compatibility alias, dual-write, or fallback path between preview catalogs.
Re-run `groundwork schema emit` and rebuild any assembly carrying a generated
`GroundworkSchema` attribute before applying to the fresh catalog.

A catalog left over from an earlier preview is refused by name rather than
failing opaquely: `GW-SCHEMA-006` names the storage unit and the discard remedy,
and the `groundwork` CLI reports it as a validation failure.

## Source-breaking provider seam

A provider package that implements the schema-tool plug-in must expose the
physicalization its runtime coordinator uses:

- `ISchemaToolProviderSession` gains `IPhysicalSchemaTargetCompiler Targets`.
- `RelationalSchemaToolSession`'s constructor takes a required
  `Func<StorageUnit, PhysicalSchemaTarget> compile` after its executor; pass the
  coordinator's own physicalization so a deployed target and the runtime's
  expected target stay one value.

A provider-owned schema definition whose payload changes — a SQL Server batch
table type follows its unit's columns, for example — now re-applies under
explicit authorization rather than being refused as non-additive.

## Authorized destructive, rename, and alter operations

Schema planning is no longer additive-only. `PhysicalSchemaOperationKind` gains
`RenamePrimaryStorage`, `RenameColumn`, `AlterColumn`, `DropColumn`, `DropIndex`,
and `DropPrimaryStorage`, and every applied definition a declaration changed,
renamed, or removed is now planned as one of them instead of being refused ahead
of the authorization model. Each flows through the existing plan-fingerprint plus
per-operation-identity authorization; nothing became blanket-authorizable.

- **Renames key on the logical id.** `ColumnDefinition.Id` joins `StorageUnit.Id`
  as a stable logical identity that defaults to the physical name. Keep the
  original id while changing `Name` and the change plans as a rename that carries
  its rows; drop the id and the same edit plans as a drop plus an add. The
  canonical schema document and `[GwTable]` / `[GwColumn]` accept `Id`, which is
  emitted only when it diverges from the name — so no already-emitted schema
  fingerprint changes.
- **Widening is semantic, narrowing is destructive.** String length up, decimal
  precision up at an unchanged scale, and required → optional are authorized with
  `--allow-semantic`; the reverse directions and any type change are authorized
  with `--allow-destructive`.
- **Any index redefinition is a rebuild.** The two earlier ad-hoc rebuild escapes
  are replaced by one rule. This corrects a real staleness bug: re-issuing
  `CREATE INDEX IF NOT EXISTS` for a changed index is a no-op on every provider
  and left the deployed index on its old partial-index filter.
- **Operations carry a readable address.** `--allow-destructive
  drop-column:orders.legacy_total` authorizes exactly one operation in exactly
  one plan, alongside the exact operation identity that still works. Where a plan
  would let one address name two operations, the address is withdrawn.
- **Removing a unit is declared, not inferred.**
  `SchemaEvolutionMetadata(retiresPrimaryStorage: true)` plans one authorized
  `DropPrimaryStorage`, after which the applied ledger holds nothing for that
  unit.

`RelationalDialect` gains `DropProviderDefinition`, the counterpart to
`ApplyProviderDefinition`. A provider-owned definition names itself after its
storage — SQL Server's batch table type embeds the table name, and the derived
search-key algorithm record is keyed on it — so a rename or a retirement left
the old object behind. Renames now carry provider definitions the same way they
carry indexes, and retirement removes them. A dialect that materializes nothing
in `ApplyProviderDefinition` inherits the empty default and needs no change.

Startup auto-apply now refuses unauthorized work with `GW-SCHEMA-007`
(destructive) and `GW-SCHEMA-008` (semantic) instead of `GW-RUNTIME-002`, which
means only index drift again. `GW-SCHEMA-003` and `GW-SCHEMA-004` are narrowed to
evolutions with no portable meaning: dropping or retyping a key column, and
renaming onto a name another applied column still holds.

MongoDB's in-process `Schema.Apply` keeps no applied ledger, so it cannot tell a
renamed field from a new one. A declaration whose logical id has diverged is
refused there with `GW-SCHEMA-009` rather than silently reading nulls; the
deployment tool plans the same rename against MongoDB's applied schema ledger and
carries it, as **MongoDB joins the deployment tool** below describes.
`Groundwork.Testing`'s in-memory reference provider keeps its additive-only
contract and refuses removals with `SchemaConflictException`. That divergence
from the shipped providers is tracked as
[#214](https://github.com/valence-works/groundwork-v2/issues/214).

`connection.Schema.Apply(unit)` takes no authorization callback, so it performs
only what re-applying the same declaration could put back — creates, adds,
renames, widenings, index rebuilds, derived backfills, and index removals — and
refuses to destroy what it could not restore. Dropping a column or its storage,
and narrowing a column past the values in it, throw `GW-SCHEMA-010` naming the
operation to authorize through the `groundwork` CLI. `Schema.Diff` still reports
those as pending.

`SchemaChangeKind` gains `RenameStorageUnit`, `RenameColumn`, `AlterColumn`,
`DropColumn`, `DropIndex`, and `DropStorageUnit`, and one shared
`SchemaChangeMapping` replaces the copy each relational coordinator carried. The
mapping is now total: an unmapped operation kind throws instead of falling into a
default bucket. The previous default described every new kind as adding a derived
column, which the weaker startup test in `GroundworkAdmissionRunner` reads as
additive — so a host with auto-apply enabled would have treated a column drop as
safe startup work. A `RebuildPhysicalIndex` now describes itself as
`RebuildIndex` rather than `CreateIndex`, which likewise stops a destructive
rebuild from reading as additive there.

## New package: `Groundwork.Extensions.DependencyInjection`

Dependency injection and hosting integration. `AddGroundwork()` declares named
connections through the options pattern and resolves them as keyed or unkeyed
services; connections are process singletons and sessions and units of work come
from a scoped `IGroundworkStorage` that disposes any unit of work its scope did
not commit.

The lifetime model is enforced rather than documented. The registration surface
has no lifetime setting, and a storage connection registered by hand with a
scoped or transient lifetime is refused at the first connection open with
`GW-HOST-001` naming the offending service type and the fix. Startup admission
runs as a hosted service before the host serves: pending unit- or column-level
schema work refuses startup with `GW-HOST-005`, index-level work degrades, and a
required capability the deployed database does not advertise refuses with
`GW-HOST-006`. A health check reports the same verdict together with the live
capability advertisement. Runtime remains inspect-only by default;
`AutoApplyOnStartup` is off by default and applies additive plans only.

The package references `Groundwork.Store` and `Groundwork.Kernel` and no
provider: provider selection travels through `IStorageProviderFactory`. An
architecture test enforces that boundary.

`samples/Groundwork.Samples.Api` is a runnable ASP.NET Core application covering
declaration, schema deployment, typed CRUD, a covered query with paging, a unit
of work, optimistic concurrency, and tenant scopes, switchable across all four
providers from configuration.

## Foreign columns are drift, and can be tolerated by declaration

A deployed column the declaration does not describe is now `GW-RUNTIME-001`. **This is a change in
default behaviour**: nothing anywhere used to look for one. Schema inspection iterated the declared
columns and never asked what else the table held, so a foreign column that is not nullable, not
defaulted, and not database-generated passed admission at startup and then failed every insert at
runtime, far from its cause. It is now refused where it can be explained.

A catalog another tool has extended therefore fails admission where it previously started. The
remedy is one line on the declaration:

- Fluent: `.TolerateForeignColumns()`
- Declaration: `ForeignColumns = ForeignColumnPolicy.TolerateDatabaseSupplied`
- Attribute: `[GwTable("orders", ForeignColumns = SchemaForeignColumns.TolerateDatabaseSupplied)]`
- Schema document: `"foreignColumns": "TolerateDatabaseSupplied"`

The opt-in downgrades a foreign column to a `GW-RUNTIME-003` warning **only** where the database
supplies its value — nullable, defaulted, or generated — because that is the whole of what tolerance
can mean: a column Groundwork can leave out of every statement it writes. A foreign column a write
that omits it would fail on stays `GW-RUNTIME-001` under the opt-in, since no policy makes it
writable. Tolerated columns are reported at every level that saw them — the admission log, a `Trace`
warning at session open, and CLI `diagnostics` at `severity: "warning"` — so the opt-in cannot be
mistaken for ignoring drift. Declared-column drift and index drift are untouched.

One rule decides this, `ForeignColumnAdmission.Classify` in the kernel: providers report the facts
they can read from a catalog and the kernel decides what they mean, so a foreign column cannot mean
one thing at startup and another at deploy time.

A column retained through an expand–contract window is **not** foreign. It is absent from the
subject's declared columns by construction — a declaration that both supersedes a column and still
declares it is refused — but the declaration names it in `Evolution.Supersessions` and deliberately
keeps it in the catalog, so the scan exempts it. Without that, an expand would refuse its own
retained column and the window could never be served.

The policy is deliberately **not** part of `SchemaSubject.Fingerprint` and is not persisted in
applied state. The fingerprint answers one question — is the deployed catalog the shape this build
compiled — and a foreign column is by construction not part of that shape. Folding tolerance into it
would make turning the setting on look like a schema change, force a no-op apply to clear it, and
split the deployment tool's compiled target from the host's. The canonical schema document does
carry it, and emits it only once it diverges from the default — so a document written before the
member existed keeps the exact fingerprint it was emitted under, and every already-written history
row stays byte-identical.

## `groundwork adopt`

`groundwork adopt --schema … --provider … --safe` records that a catalog Groundwork never applied is
nevertheless exactly what applying the compiled target would have produced. It is the opposite of
the inference `GW-SCHEMA-001` refuses, and that refusal is unchanged: nothing reads a deployed
column and decides what it probably corresponds to. The target comes from the declaration, the
catalog is compared to it in full under the application lock that will publish the claim, and any
difference is a refusal naming what differs. Arbitrary legacy-schema mapping stays out of scope.

The published row is not assembled by the adoption path. It is produced by
`PhysicalSchemaDiffPlan.Complete` from the same plan a real apply would have run, so an adopted row
and an applied row are the same value and the next diff reasons from the same premise either way.
Authorization is apply's, unchanged: `--safe`, or `--expected-plan` naming the plan fingerprint.

Adoption refuses, publishing nothing, when history is already recorded (`GW-SCHEMA-011`), the
subject is declared retired (`GW-SCHEMA-012`), the provider called the catalog invalid without
naming what differs (`GW-SCHEMA-013`), or the provider cannot compare a catalog to a target at all,
which is `GW-CLI-013` by name rather than a generic execution failure. Every provider Groundwork
ships is a catalog inspector, MongoDB included, so that last refusal is for a third-party plug-in.
A folded (search-key) column cannot be adopted: its algorithm registration lives
in Groundwork's own catalog, which a database Groundwork never applied to does not have, so the
column's contents cannot be shown to have been produced by the declared algorithm. That refusal is
`GW-RUNTIME-001` naming the algorithm.

Adoption verifies shape, not contents.

## MongoDB joins the deployment tool

`MongoSchemaExecutor` implements `IPhysicalSchemaExecutor`,
`IPhysicalSchemaHistoryInspector` and `IPhysicalSchemaCatalogInspector`, and
`MongoSchemaToolProviderSessionFactory` publishes it under the alias `mongodb`.
`groundwork plan`, `validate`, `status`, `apply` and `adopt` now reach MongoDB
through the same session contract as the relational providers, against a replica
set or a sharded cluster. A standalone deployment is refused by name when the
session opens: publishing the ledger and the provider catalog together needs a
transaction, and saying so up front beats failing part-way through an apply.

The applied schema ledger and the application lease live in
`__groundwork_metadata`, beside the provider catalog the runtime already keeps
there, and the ledger holds exactly the canonical JSON
`PhysicalSchemaAppliedStateSerializer` produces for every other provider. One
plan and report format therefore spans a table and a collection: operation kinds,
operation identities, authorization addresses, refusal codes and exit codes are
the same values, and only the target fingerprint differs, because it names the
provider by construction.

Planned operations become collection, index, document and metadata work.
`CreatePrimaryStorage` creates the collection, `AddColumn` materializes the field
on documents that predate it, `BackfillColumn` writes the portable default or
recomputes the folded search key, `RenameColumn` moves the stored field,
`AlterColumn` re-encodes stored values when the BSON representation changes,
`DropColumn` unsets it, and the index operations create, rebuild or drop.
`FinalizeColumn` does nothing: MongoDB stores no per-field nullability to switch,
and what proves the documents honour a required column is `ValidatePhysicalSchema`
at the end of the plan. A subject that is scoped owns one collection per scope,
and index, field and validation work spans every one of them.

Two properties differ from the relational executor by necessity, and are stated
rather than papered over:

- **A batch is not one transaction.** MongoDB cannot run `drop` or
  `renameCollection` inside a multi-document transaction. Every operation is
  individually idempotent instead — create if absent, set where missing, drop if
  present — and applied state is published only after all of them succeed, so an
  interrupted apply replans from the ledger it never wrote and re-runs onto the
  state it left.
- **A field the declaration does not mention is not a foreign column.** MongoDB
  publishes no column catalog, so `ForeignColumnPolicy` has nothing to classify:
  there is no undefaulted `NOT NULL` column that could refuse a write. Declared
  columns are still verified against the documents, and a missing field or a
  wrong BSON type is `GW-RUNTIME-001` drift as it is everywhere else.

`groundwork adopt` works against MongoDB. It compares the deployed collection set
— the primary collection, every per-scope collection, their indexes, the declared
fields in their documents, and the registered folded search-key algorithms —
against the compiled target, and publishes the applied state an apply would have
produced. A difference is refused by name, publishing nothing. `GW-CLI-013` no
longer names MongoDB: it is the refusal for a provider that cannot compare a
catalog to a target at all, which now means a third-party plug-in.

`GW-SCHEMA-009` changes meaning. MongoDB can carry a column's logical id across a
rename, because `groundwork apply` plans that rename against the applied ledger.
The code remains, narrowed to the in-process `connection.Schema.Apply(unit)`
path, which plans from the fingerprint in `__groundwork_metadata` rather than
from that ledger and so still cannot tell a renamed field from a new one. Its
message now says exactly that and points at the deployment tool. Expand–contract
is likewise no longer excluded: MongoDB has both an applied schema ledger and a
data-migration ledger, so `--phase contract` gates on `GW-EXPAND-002` and then
removes the superseded column like any other provider.

**MongoDB catalogs are affected by the persisted schema boundary above.**
MongoDB's own `__groundwork_metadata` fingerprint now orders declared indexes and
aggregation profiles canonically, as `SchemaSubject` already did. A schema
document canonicalizes their order and the fluent builder does not, so the
order-sensitive hash refused a declaration the deployment tool had just applied.
Discard MongoDB catalogs created by an earlier preview along with the rest.

## The declared key is query coverage

A read bounded by the declared key is now **covered**, on the same terms as a read
bounded by a declared index. `Where(x => x.Id == id)` used to be refused as
uncovered by all three gates, and the refusal advised declaring an index on the
key column — which would have produced a second physical index identical to the
primary key.

This is a **behaviour change**: query shapes that used to refuse now execute.
Nothing that was covered before becomes refused.

Where the candidates come from is now one derivation, `CoverageCandidates.Derive`,
used by the analyzer, `SchemaVerifier`, and the runtime gate the LINQ executor
builds. The key leads the candidate list; the declared indexes follow.

**The boundary of the rule.**

- The key is an **ordered** candidate, not a set of columns. A composite key
  `(tenant, id)` covers a predicate on `tenant`, and on `tenant` and `id`
  together; it does not cover a predicate on `id` alone, exactly as a declared
  compound index on those columns would not.
- The key is **not** subject to the declared-versus-deployed intersection that
  guards declared indexes. A declared index can be absent from the catalog part
  way through a rolling deploy; the key cannot, because the coordinator emits it
  as the `PRIMARY KEY` of the `CREATE TABLE` itself.
- A refusal never advises declaring an index over the **leading columns of the
  key**. Where that is what the checker would otherwise compose, the suggestion is
  withheld and the point-read path is named instead: `session.Read(key)`, or the
  typed `Records` read.
- **MongoDB is not yet an index seek for this shape.** MongoDB stores the key in
  `_id` but persists the key columns as ordinary fields, and the renderer filters
  on those fields, so `find({ id: … })` is a collection scan; a composite `_id`
  gives no prefix seek either. The gate's verdict is the same on all four
  providers, but the physical plan on MongoDB is not yet. That gap is tracked in
  [#238](https://github.com/valence-works/groundwork-v2/issues/238) and is not
  closed by this change.
- **A scoped unit is unchanged, and still refuses.** The runtime gate builds its
  candidates from the physicalized unit, whose indexes and key both carry the
  provider-owned scope column, so a `ScopePolicy.Scoped` unit refuses reads the
  analyzer covers — for a declared index as much as for the key. That predates
  this change, which neither widens nor narrows it; it is tracked in
  [#239](https://github.com/valence-works/groundwork-v2/issues/239).
- The 250-case LINQ conformance corpus is unaffected: it pins the `GW-LINQ-1xx`
  lowering vocabulary, not coverage verdicts, and it passes unchanged.

## Other changes

- The `[GwTable]` attribute surface declares the lifecycle policies the fluent
  builder can: scope, an optimistic concurrency token, timestamps, column
  defaults, retention, append and retention idempotency, and aggregation
  profiles through `[GwRetention]`, `[GwAppendIdempotency]`,
  `[GwRetentionIdempotency]`, and `[GwAggregate]`.
- A timestamp default without an explicit offset is read as UTC, so a canonical
  document and its fingerprint no longer depend on the machine that compiled it.
- Malformed canonical documents are refused as validation errors naming the
  property, rather than surfacing as generic execution failures.
- SQLite refuses a second connection to the same database file with the stable
  code `GW-SQLITE-LIFETIME-001`. The previous message attributed the held schema
  lock to "another Groundwork process" even when the second connection was
  opened by the same process, which is the more common hosting mistake; the new
  message names the file, the one-connection-per-file rule, and what to do in
  hosts, tests, and tools.
- PostgreSQL creates the append idempotency ledger and the sequence high-water
  table lazily, on the first write that needs them. That bootstrap is now
  serialized on the name of the object it creates, with the same
  `pg_advisory_xact_lock` the dialect already uses for schema infrastructure.
  PostgreSQL's `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` are
  check-then-act rather than atomic, so two application instances issuing their
  first idempotent append at once — a cold start or a rolling deploy — could both
  find the ledger absent and leave the loser with a raw `23505` on a shared
  catalog index instead of a Groundwork outcome. A steady-state append reads the
  catalog once, issues no DDL, and takes no lock.
