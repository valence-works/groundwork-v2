# Groundwork v2 0.4.0-preview.2

This patch preview fixes MongoDB exact-batch transaction atomicity. All public
packages and `Groundwork.Tool` use the exact immutable version
`0.4.0-preview.2` and are published only to the Valence Works Groundwork Feedz
source.

## Release identity and compatibility

The production source for this release is commit
`70697165299993b2bd140ed908fae327bb11941f`. The release-preparation commit
changes only release metadata, documentation and install/version pins; it does
not change `src/`, `samples/`, or `benchmarks/`. Package repository metadata on
every artifact identifies the tagged release commit.

All 26 package identities in `eng/public-packages.txt` remain one versioned
closure and must be upgraded together. This release preserves the public API,
diagnostic inventory, and persisted catalog contract from `0.4.0-preview.1`.
Existing `0.4.0-preview.1` catalogs remain compatible: no discard, migration,
or schema re-application is required.

## MongoDB exact-batch transaction atomicity

On a transaction-capable MongoDB deployment, an exact batch inside an explicit
unit of work now treats a modeled create-only or compare-and-swap conflict as a
transaction outcome rather than a successful partial batch:

- execution stops at the first modeled conflict, so no trailing operation is
  attempted;
- the active transaction aborts and the explicit unit of work becomes terminal;
- the caller receives the provider-neutral `BatchWriteException`; and
- wrapper-owned exact-batch transactions do not commit the losing operation or
  any earlier operation in that batch.

The same behavior applies to synchronous and asynchronous create-only and
compare-and-swap batches. Retention processing is not entered after an aborting
outcome. Live replica-set conformance covers the winning state and verifies that
the losing batch's trailing row is absent.

Standalone MongoDB deployments retain their advertised capability boundary:
transaction-required exact-batch behavior is not emulated without transaction
support.

## MongoDB JSON scalar admission

MongoDB schema and runtime admission now accept every native BSON representation
produced by the portable JSON codec: objects, arrays, strings, numbers, booleans,
and JSON literal `null`. A required JSON column continues to reject a missing
value or CLR `null`, while a JSON literal `null` remains valid JSON content. The
codec also refuses Mongo-only BSON values, including dates and object identifiers,
before they can create write/admission disagreement.

## Upgrade

Pin every Groundwork package and the tool to `0.4.0-preview.2`, restore the
complete closure from the Feedz source, and deploy normally. Do not mix
`0.4.0-preview.1` and `0.4.0-preview.2` packages in one process.
