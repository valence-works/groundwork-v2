# Groundwork v2 0.4.0-preview.4

This patch preview fixes index-compatible relational ordering. All public
packages and `Groundwork.Tool` use the exact immutable version
`0.4.0-preview.4` and are published only to the Valence Works Groundwork Feedz
source.

This preview also adds the optional bounded affected-key evidence contract for
operation-identified retention (`RetentionAffectedKeyProjection`,
`RetentionOperationResult.AffectedKeys`, and
`IExactRetentionAffectedKeysStorageSession`). InMemory, SQLite, PostgreSQL, SQL
Server, and transaction-capable MongoDB enforce native `bound + 1` refusal,
canonical replay/conflict semantics, and atomic ledger/row mutation; standalone
MongoDB omits the capability. The public bound is capped at 1,000,000 values,
and binary projections require a positive declared `MaxLength` of at most 16
MiB, so every admitted executed result remains replayable by the durable codec.

## Native substring matching over string arrays

`Predicate.ElementSubstring` adds provider-neutral `Contains` and `EndsWith`
matching against each element of a typed string array. InMemory evaluates the
same ordinal and explicit ASCII ignore-case policies admitted by the native renderers;
Unicode ordinal ignore-case is refused for raw arrays because it requires a persisted,
versioned per-element search key.
SQLite, PostgreSQL, SQL Server, MySQL/MariaDB, and MongoDB expand arrays on the
server; adjacent elements are never joined, and malformed, missing, null, or
empty owners fail closed. The operation is bounded-scan-only until a compatible
element search-key index is declared, so query coverage refuses it unless the
caller records an explicit accepted scan.

## Refuse hosted schema auto-apply outside Development

`Groundwork.Extensions.DependencyInjection` now refuses startup when a named
connection enables `AutoApplyOnStartup` in Production or any other
non-Development host environment. The refusal is `GW-HOST-007` and happens
before startup admission can ask a provider to mutate schema, so a production
host cannot silently behave like `EnsureCreated` and then report a successful
startup. Review the deployment plan with `groundwork plan`, then use the
explicit `groundwork apply --safe` deployment path. Development hosts retain
the existing opt-in safe-plan auto-apply and warning; tests must either run with
the Development environment or apply schema explicitly through
`connection.Schema.Apply`. A directly constructed `GroundworkAdmissionRunner`
is inspect-only because it has no trusted host-environment context.

## Release identity and compatibility

The production source for this release is the merge of PR #365 to `main`,
commit `512636524a343d30f15df5cf472cb0bbc36b9be9`. The release-preparation
commit changes only release metadata, documentation, and install/version pins;
it does not change `src/`, `samples/`, or `benchmarks/`. Package repository
metadata on every artifact identifies the tagged release commit.

All 26 package identities in `eng/public-packages.txt` remain one versioned
closure and must be upgraded together. This release preserves the public API,
diagnostic inventory, and persisted catalog contract from `0.4.0-preview.3`.
Existing `0.4.0-preview.3` catalogs remain compatible: no discard, migration,
or schema re-application is required.

## Index-compatible relational ordering

Relational renderers now use the selected provider-resolved index declaration
to omit a redundant null-rank expression only when that declaration proves the
ordered column is non-nullable. This lets matching composite indexes satisfy
the requested order without an unnecessary sort. Nullable or unproven columns
retain Groundwork's explicit portable null ordering.

PostgreSQL, SQL Server, MySQL, and SQLite retain their provider-specific
ordinal string, decimal, GUID, and keyset-continuation semantics. The public
renderer surface is unchanged. The correction is covered by renderer,
architecture, public-API, differential, and isolated live-provider gates.

## Distribution workflow

This preview is Feedz-only. Publishing the GitHub release starts
`publish-feedz.yml`; it does not start the nuget.org workflow. A maintainer who
intentionally wants this exact package closure on nuget.org must manually
dispatch `publish-nuget.yml` against the release tag with `publish=true` and
the exact version repeated in both `version` and `confirm`. That manual path
retains the full package/test, layout, clean-room, integrity, credential,
symbol, protected-environment, and post-publication exact-version restore
gates.

## Isolated schema-tool deployment

`Groundwork.Tool` now embeds the first-party schema provider plug-ins. A fresh tool installation
loads the `sqlite`, `postgresql`, `sqlserver`, `mongodb`, and `mysql` aliases without an application
build or a custom host. Third-party providers continue to use `--provider-assembly <file>`.

The deployment step can therefore run directly in a CI image:

```bash
groundwork apply --schema groundwork.schema.json \
  --provider sqlite --database ./app.db --safe
```

Subcommand help is available (for example, `groundwork apply --help`), and an execution failure's
concise inner exception detail is included in `GW-CLI-010` after the existing connection-secret
redaction.

## Upgrade

Pin every Groundwork package and the tool to `0.4.0-preview.4`, restore the
complete closure from the Feedz source, and deploy normally. Do not mix
`0.4.0-preview.3` and `0.4.0-preview.4` packages in one process.
