# Streams: Sequences, Append & Retention

Four opt-in capabilities that together let you build durable, restart-safe streams — event logs,
outboxes, audit trails — without writing provider-specific plumbing.

| Capability | Declare | Gives you |
| --- | --- | --- |
| Provider sequence | `ColumnGeneration.ProviderSequence` | A monotonic `Int64` key assigned by the database |
| Idempotent append | `AppendIdempotency(window)` | Replay-safe batch writes under an operation id |
| Retention | `Retention(...)` / `KeepNewest(...)` | Bounded, resumable newest-N cleanup |
| Durable lifecycle | `RetentionIdempotency(window)` | Replay-stable retention + durable high-water inspection |

---

## Provider-assigned sequences

```csharp
var unit = StorageUnit.Declare("events", "events")
    .Int64("sequence", c => c.Required().ProviderSequence())
    .String("payload", 200, c => c.Required())
    .Key("sequence")
    .Build();

var outcome = session.Insert(new StorageValues(new Dictionary<string, object?>
{
    ["payload"] = "created"     // the key is NOT supplied
}));

long sequence = outcome.GeneratedValue<long>("sequence");
```

### Rules

- The column must be **non-nullable `Int64` and the sole primary-key column** (`GW-PORT-005`).
- Supplying its value on `Insert` is refused.
- Allocation is **strictly increasing**: if allocation A precedes B in the provider's serialization
  order, A's value is lower.
- **Concurrent transactions can commit or become visible in a different order**, so the value is *not*
  a commit-order timestamp. Do not use it to reconstruct causality.
- **Gaps are valid.** A failed or rolled-back allocation does not invalidate later values. Never
  assume density.
- The value is the identity used to read the committed row.
- `Update`/`Upsert` may supply an already-generated key **as a locator**. It is excluded from
  mutation, and a locator `Upsert` returns `NotFound` rather than inserting when the key is absent.
  Omitting the key on `Upsert` requests a **new** generated row.

### Provider realization

| Provider | Mechanism | Extra commands per insert |
| --- | --- | --- |
| PostgreSQL | `GENERATED BY DEFAULT AS IDENTITY`, read from `RETURNING` | 0 |
| SQL Server | `IDENTITY(1,1)`, read from `OUTPUT INSERTED` | 0 |
| SQLite | `INTEGER PRIMARY KEY AUTOINCREMENT`, read from `RETURNING` | 0 |
| MongoDB | `FindOneAndUpdate` on the `__groundwork_sequences` counter, in the **same transaction** | **1** |

For scoped SQLite units the generated value remains **unit-wide** — scope is an access predicate, not
an extra physical primary-key column.

MongoDB sequences require a **transaction-capable replica set or sharded deployment**.
`IMongoProviderConnection.ProviderSequenceFit` reports `ProviderFit.Unsupported` on standalone, and
the capability is omitted from the runtime advertisement.

> **MongoDB + conditional upsert:** `ConditionalUpsert` refuses `ProviderSequence` columns —
> allocation needs a separate command and a transaction, which would violate the one-command
> contract. Use ordinary `Insert`/`Upsert`.

For MongoDB direct writes, transient conflicts inside Groundwork's internally owned transaction
replay the complete counter-and-row operation; an unknown commit result retries only the commit.
**Explicit units of work stay caller-owned and surface body conflicts** — replaying later caller
actions would not be safe.

## Idempotent append

Retries are inevitable. `AppendIdempotency` makes them free.

```csharp
var unit = StorageUnit.Declare("events", "events")
    .String("id", 450, c => c.Required())
    .String("payload", 450, c => c.Required())
    .Key("id")
    .AppendIdempotency(window: TimeSpan.FromMinutes(10))
    .Build();

var operation = new OperationId(DateTimeOffset.UtcNow, "import-2026-08-15-001");

var first  = session.Append(operation, values);   // Status == Inserted
var replay = session.Append(operation, values);   // Status == Replayed — nothing written
```

`OperationId` is `(DateTimeOffset IssuedAt, string Nonce)`. **The timestamp is metadata only** —
expiry is evaluated against the provider's *recorded ledger time*, not your clock. That is what makes
it correct under clock skew.

Every provider owns the durable ledger and commits its `(unit, scope, nonce)` entry **with the payload
rows in one transaction**. Once the recorded entry expires, the same nonce is admitted again. Expired
entries are reclaimed in bounded batches, so retention work cannot grow a single append without limit.

Advertised as `BatchWriteCapabilities.AppendIdempotency`.

### Exact append outcomes

When you need the provider-generated values back — and the same values on replay:

```csharp
var first  = session.AppendWithOutcomes(operation, values);
var replay = session.AppendWithOutcomes(operation, values);

long sequence = replay.Outcomes[0].GeneratedValue<long>("sequence");
// Identical to first.Outcomes[0]. No new sequence was allocated.
```

The ledger stores a **versioned, injective fingerprint** of the declared portable input values plus
the versioned exact outcome payload, in the same transaction as the rows.

| Code | Meaning |
| --- | --- |
| `GW-APPEND-001` | Same unit/scope/nonce reused with a **different payload**. Nothing is written. |
| `GW-APPEND-002` | Legacy ledger entry has no persisted generated values; exact replay refuses. (Status-only `Append` still replays it.) |
| `GW-APPEND-003` | Provider does not advertise exact append. Refused **before** any write. |

The fingerprint encoding is strict about text: malformed UTF-16 is refused before the ledger is
consulted. Declared decimals use **numeric value rather than scale**, JSON object properties are
sorted, and numeric lexemes such as `1`, `1.0`, and `1e0` are normalized **without** going through a
lossy floating-point representation. So equivalent portable values replay, while a genuinely changed
value still produces `GW-APPEND-001`.

Advertised as `BatchWriteCapabilities.ExactAppendOutcomes`.

## Retention

Opt-in, provider-neutral, **count-based**:

```csharp
Retention = new RetentionDeclaration
{
    KeepNewest       = 100,
    OrderColumn      = "sequence",
    PartitionColumns = ["tenant"],
    Trigger          = RetentionTrigger.Explicit   // or OnAppend
}
```

```csharp
var result = session.ApplyRetention(new RetentionExecutionOptions { MaxRowsPerBatch = 128 });
```

- `KeepNewest = 0` is portable and means **delete every retained row in each partition**. The
  lifetime sequence high-water is **not** reset.
- `MaxRowsPerBatch` makes a pass **interruptible**: cancellation is checked between bounded delete
  commands, and a later pass recomputes the watermark and resumes safely.
- Invalid declarations are refused with `GW-PORT-007` before schema I/O — negative `KeepNewest`, a
  missing/nullable/non-orderable order column, or a missing partition column.

### `RetentionTrigger.OnAppend`

Bounded cleanup runs after a successful single-row append, a newly inserted idempotent append, an
inserted conditional upsert / `CreateOnly`, or a native batch append.

Concurrent committed appenders **coalesce on a per-unit/per-scope dirty signal**: one owner recomputes
retention until the signal drains, while other writers return immediately rather than queueing behind
cleanup. An idempotency replay never rewrites its payload and may safely drain a pending cleanup —
which is how an interrupted post-commit cleanup converges on the declared watermark.

SQL Server and SQLite register appenders **before** their shared write gates and run coalesced cleanup
only after the successful write transaction releases that gate.

### Provider implementations

| Provider | Approach |
| --- | --- |
| Relational | `ROW_NUMBER()` ranking; deletes only rows beyond newest-N in **one bounded statement per pass** |
| MongoDB | Disk-spillable bounded-batch partition projection, then at most one configured batch of identities beyond each partition's watermark → `deleteMany` |

MongoDB **never** gathers every identity in a partition into an array, and its order-column/primary-key
sort preserves the same deterministic tie-break as the other providers.

> MongoDB deliberately does **not** use capped collections: a cap is collection-wide, cannot express
> N rows per partition, and prevents normal document growth and index updates.

On cancellation, SQL providers roll back the interrupted pass; MongoDB may leave a completed bounded
batch. Both resume by recomputing the watermark and converge on the exact retained count.

## Durable lifecycle capabilities

```csharp
var unit = new StorageUnit
{
    // columns and key omitted
    Retention = new RetentionDeclaration { KeepNewest = 100, OrderColumn = "sequence" },
    RetentionIdempotency = new RetentionIdempotencyDeclaration
    {
        Window     = TimeSpan.FromHours(24),
        LedgerName = "stream_retention_operations"
    }
};

var highWater = session.Inspect().LifetimeCommittedSequenceHighWater;

var result = session.ApplyRetention(
    new OperationId(DateTimeOffset.UtcNow, "retention-cycle-2026-08-16"),
    new RetentionExecutionOptions { MaxRowsPerBatch = 128, KeepNewestOverride = 10 });
```

### Durable high-water inspection

`IStorageInspectionSession` reports `LifetimeCommittedSequenceHighWater`:

- **Null means empty** — distinct from a committed sequence value.
- Keyed by unit **and scope**.
- Updated in the **same transaction** as the generated row.
- **Survives retention deleting rows** and a provider/session restart.
- A rollback **never** advances it.

That combination is what lets a consumer restart and know where it was, even after cleanup removed
the rows it had processed.

| Code | Meaning |
| --- | --- |
| `GW-INSPECT-001` | Provider does not advertise durable inspection |
| `GW-INSPECT-002` | Unit has no `ProviderSequence` column |

### Exact (operation-identified) retention

`IExactRetentionStorageSession` uses `RetentionIdempotencyDeclaration` — deliberately **separate**
from `AppendIdempotency`, because append replay lifetime and retention replay lifetime are
independent policies.

The ledger stores a canonical request fingerprint and a versioned exact result.

| Code | Meaning |
| --- | --- |
| `GW-RETENTION-001` | Same nonce, **changed request** (including the effective keep value). Refused before changing rows. |
| `GW-RETENTION-002` | Malformed/legacy exact result. Remediation: use a new nonce. |
| `GW-RETENTION-003` | Provider does not advertise exact retention |
| `GW-RETENTION-004` | `RetentionIdempotency` declared **without** `Retention` |
| `GW-RETENTION-005` | Bounded affected-key projection exceeded its finite maximum; no rows changed |
| `GW-RETENTION-006` | Status-only retention received an affected-key projection |
| `GW-RETENTION-007` | Provider does not advertise bounded affected-key retention |

`KeepNewestOverride` is an optional non-negative per-pass value: null uses the declaration, a positive
value keeps that many, and **zero deletes every row without resetting the durable high-water**. The
effective value is part of the fingerprint, so a same-nonce retry with a different override is refused.

#### Bounded affected-key evidence

An operation-identified pass can return the complete distinct values of one declared scalar column
from the rows it removes:

```csharp
var result = session.ApplyRetention(
    operation,
    new RetentionExecutionOptions
    {
        MaxRowsPerBatch = 128,
        AffectedKeyProjection = new RetentionAffectedKeyProjection("tenant", 100)
    });
```

The finite bound is strict and cannot exceed 1,000,000 distinct values: providers read at most
`bound + 1` values natively and refuse with
`GW-RETENTION-005` before mutating rows or claiming the ledger when the bound is exceeded. A
successful `AffectedKeys` list is complete, distinct, null-first, and deterministically ordered
using Groundwork's portable structural comparison. The projection, bound, scope, and operation
identity participate in the canonical fingerprint; the same nonce and request replays the exact
same result, while changing any of them is `GW-RETENTION-001`. JSON and Double projections are
refused as non-orderable. Binary projections require a positive declared `MaxLength` no greater
than 16 MiB, matching the exact-result codec's replay-safe value limit. Inspect
`IExactRetentionAffectedKeysStorageSession` and
`BatchWriteCapabilities.ExactRetentionAffectedKeys` before requesting this optional contract.

Exact retention is **atomic at the provider boundary**: the bounded delete loop, ledger placeholder,
and final result update share one transaction. Cancellation or a failed batch rolls back the whole
pass including the ledger, so a retry executes once and its later replay returns the same cumulative
result.

Status-only `ApplyRetention()` keeps the existing resumable behavior and needs no idempotency
declaration.

### Ledger naming

Append and retention declarations must use **distinct** ledger names. Groundwork reserves its
metadata, schema, search-key, high-water, and default operation ledger names; custom declarations
cannot claim them.

> **SQL Server:** lifecycle identity columns are created with `Latin1_General_100_BIN2` so unit,
> scope, and nonce values use ordinal identity semantics. Existing lifecycle tables with a different
> collation are **refused with migration guidance** (`GW-SQLSERVER-LIFECYCLE-001`) rather than
> silently merging case-distinct identities.
